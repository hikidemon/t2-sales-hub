# Резервная авторизация: вход по ПИН

Если вход через портал ABC T2 (T2 ID) не выдадут, кабинет всё равно
должен быть закрыт для посторонних. Этот документ описывает запасной
вариант, который работает **сегодня** и не требует ничего от
корпоративного IT.

## Чем подтверждается «настоящий сотрудник»

Человек считается сотрудником, если его **есть в справочнике**.
Справочник — это список сотрудников с их торговыми точками и ролями;
он ведётся администратором и лежит только на сервере.

| Источник доверия         | Что подтверждает                     | Нужно от компании           |
| ------------------------ | ------------------------------------ | --------------------------- |
| **T2 ID** (`auth.t2.ru`) | подтверждает сам корпоративный центр | выпустить клиент приложения |
| **Справочник + ПИН**     | администратор выдал ПИН сотруднику   | ничего                      |

ПИН — не пароль и не «знание секрета»: это персональный код, который
администратор выдаёт конкретному человеку и может отозвать. Поэтому
справочник и выдача ПИН — это и есть точка доверия.

## Как это устроено

```
браузер                          сервер
   │ POST /api/auth/pin/sign-in     │
   │  {identifier, pin} ───────────►│  1. ищет сотрудника в справочнике
   │                                │  2. сверяет ПИН с scrypt-хешем
   │                                │  3. проверяет лимит попыток
   │                                │  4. пишет запись в журнал
   │◄───────────────────────────────│  5. выдаёт подписанную cookie
```

Сессия — та же самая, что и при входе через портал: подписанная cookie
`t2_session`, шифрованное хранилище `.data/sessions.json`, срок жизни
30 дней. Человек входит один раз и больше не входит — даже после
перезапуска API.

## Безопасность

| Что           | Как                                                              |
| ------------- | ---------------------------------------------------------------- |
| Хранение ПИН  | только scrypt-хеш с индивидуальной солью, `scrypt$<salt>$<hash>` |
| Проверка      | `timingSafeEqual` — сравнение за постоянное время                |
| Перебор       | 5 попыток на человека и на адрес, затем блокировка на 15 минут   |
| Утечка ответа | на неверное имя и на неверный ПИН отвечают одинаково             |
| Однозначность | фамилия без имени принимается, только если она уникальна         |
| Справочник    | `.data/employees.json`, в `.gitignore`, наружу не отдаётся       |
| Журнал        | `.data/access-log.jsonl` — кто, когда, откуда и с каким исходом  |
| ПИН в журнале | не пишется никогда                                               |
| Права         | управление справочником — только для роли `admin`                |

## Включение

```env
AUTH_REQUIRED=true
AUTH_METHODS=pin
AUTH_COOKIE_SECRET=<случайная строка от 16 символов>
```

Одновременно с порталом:

```env
AUTH_METHODS=abc-t2,pin
```

Тогда интерфейс предлагает оба способа, а вход через портал остаётся
приоритетным.

## Наполнение справочника

Из исходной книги (лист «график»):

```bash
./.venv-sheets/Scripts/python.exe scripts/seed_directory.py --pin 1234
```

Скрипт берёт фамилии, должности и торговую точку и пишет
`.data/employees.json`. ПИН задаётся аргументом `--pin` — для
проверки; в рабочем режиме ПИН выдаёт администратор.

Дальше — в разделе «Управление»:

- добавить сотрудника (ПИН генерируется и показывается **один раз**);
- сбросить ПИН (новый показывается один раз);
- отключить сотрудника (учётная запись остаётся, но вход закрыт);
- удалить сотрудника;
- прочитать журнал входов.

## Кто становится администратором

Роль из справочника можно поднять из окружения — по имени, как и для
входа через портал:

```env
AUTH_ADMIN_LOGINS=Иванова Пётр Петрович
```

Роль справочника при этом не отнимается — окружение может только
добавить.

## Проверка

```bash
# сервер
cd apps/api && AUTH_REQUIRED=true AUTH_METHODS=pin \
  AUTH_COOKIE_SECRET=pin-cookie-secret-0123456789abcdef \
  DATA_SOURCE=mock PORT=3008 ./node_modules/.bin/tsx src/main.ts

# браузер
node scripts/t2-pin-browser-check.mjs 9225 http://localhost:5177/

# панель администратора
node scripts/t2-directory-browser-check.mjs 9225 http://localhost:5177/
```

## Чего этот вариант не даёт

Честно о границах:

- **Это не криптографическая идентификация.** ПИН подтверждает, что
  человек получил доступ от администратора, а не что это точно он.
  Полноценная проверка — только через корпоративный центр (T2 ID).
- **Нет второго фактора.** ПИН — единственное, что знает человек.
  Когда появится клиент в `auth.t2.ru`, лучший вариант — оставить ПИН
  как запасной, а основным сделать вход через T2 ID.
- **Справочник наполняется вручную.** Пока нет выгрузки из 1С или из
  ABC T2, сотрудников в него заводит администратор. При большом числе
  сотрудников это неудобно — тогда нужен источник кадровых данных.

## Следующий шаг, если T2 ID всё-таки выдадут

Клиент в `auth.t2.ru` + `AUTH_METHODS=abc-t2,pin` — оба способа
работают одновременно, переключение занимает одну строку в `.env`.
Код менять не нужно: провайдеры независимы.
